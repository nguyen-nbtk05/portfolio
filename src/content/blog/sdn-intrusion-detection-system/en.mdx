# Detecting and Mitigating Network Attacks in an SDN Lab

Software-defined networking moves control decisions out of individual switches and into a programmable controller. That central view makes network automation easier, but it also turns the controller and its control channel into valuable targets.

I built this lab to explore how an SDN controller can use the information it already receives to detect attacks and react automatically. The system combines OpenFlow flow statistics, Shannon entropy, destination-port analysis, and trusted MAC-IP bindings to detect DDoS, port scanning, and ARP spoofing.

## The 16-host Mininet testbed

The topology uses one Open vSwitch running OpenFlow 1.3 and sixteen Mininet hosts:

| Role | Count | Address range | Purpose |
| --- | ---: | --- | --- |
| Protected victim | 1 | `10.0.0.1` | Target service monitored by the IDS |
| Benign clients | 5 | `10.0.0.11–15` | Generate expected background traffic |
| Attackers | 10 | `10.0.0.21–30` | Generate DoS/DDoS, scan, and ARP scenarios |

The switch connects to a Ryu 4.34 controller. Ryu exposes topology and flow information through OpenFlow and its REST applications, while the detector polls statistics every five seconds.

This topology is intentionally small and deterministic. It makes attack scenarios repeatable and gives every expected source a known role, which is important when evaluating false positives and missed alerts.

## Detection pipeline

The system divides detection into two paths:

1. **Flow-based analysis** handles DoS/DDoS and port scanning from periodically collected switch counters.
2. **Packet-In analysis** handles ARP spoofing as ARP frames arrive at the controller.

Flow statistics are accumulated over four polling cycles, creating a 20-second sliding window. Aggregating several observations reduces sensitivity to a single noisy sample while keeping the response fast enough for a lab environment.

### DDoS with Shannon entropy

Entropy measures how evenly packets are distributed across observed sources or destinations. For probabilities `p₁ ... pₙ`, the detector uses:

```text
H(X) = -Σ pᵢ log₂(pᵢ)
```

A concentrated distribution produces lower entropy. The detector combines source and destination entropy with total traffic volume and the number of attacking sources. Using multiple conditions is important: low entropy alone can also occur during legitimate communication with one popular service.

The classifier distinguishes a concentrated DoS source from distributed DDoS activity and excludes traffic that has stronger port-scan evidence.

### Port scans with two signals

The primary method counts distinct destination ports for each source-to-protected-destination pair. Ten or more ports trigger the configured threshold.

Some Ryu flow-stat responses do not expose `tcp_dst` or `udp_dst`. For that case, the project includes a fallback based on packet rate and volume. Traffic between 30 and 500 packets per second with sufficient packets becomes a suspected rate-based scan.

The fallback keeps the detector useful across different OpenFlow observations, but its alert explicitly says “suspected” because packet rate is weaker evidence than a visible set of destination ports.

### ARP spoofing with trusted bindings

ARP is handled directly inside a Ryu application. The controller compares every observed sender IP and MAC address with a trusted table. A known IP claiming a different MAC produces `ARP_SPOOFING`; an IP outside the expected topology produces `ARP_UNKNOWN_BINDING`.

This path does not wait for the 20-second statistics window. ARP frames are sent to the controller through Packet-In events and evaluated immediately.

## Automated mitigation and alerts

When the detector identifies a malicious source, the mitigation module sends a high-priority Flow-Mod rule to the switch. The rule drops traffic from that source for 300 seconds. Protected addresses are checked before a rule is installed so the detector cannot accidentally block its own victim configuration.

Alerts are written as JSON Lines. Each record can include the timestamp, attack type, source, victim, traffic volume, entropy values, and explanation. Structured logs make it easier to correlate a decision with the evidence that produced it.

```json
{
  "attack_type": "Distributed_DDoS",
  "victim_ip": "10.0.0.1",
  "src_entropy": 2.91,
  "dst_entropy": 0.0,
  "action": "flow_drop_300s"
}
```

The example above illustrates the report shape; actual values depend on the traffic generated during each run.

## Reproducible evaluation

The evaluator builds the topology, launches the detector with mitigation disabled, generates benign and attack scenarios, and compares expected alerts with observed alerts. It reports precision, recall, and F1 by attack type and globally after duplicate alert pairs are removed.

Disabling mitigation during measurement matters. Otherwise, an early block changes later traffic and makes detection results harder to compare. A port-count scenario is also marked as skipped when the switch statistics do not expose transport-layer destination ports; the rate-based scenario can still run.

## Limitations and next steps

This remains a controlled Mininet experiment, not a production IDS. Detection thresholds are static, the topology has one switch, and the system has not been validated against encrypted application behavior or physical OpenFlow hardware.

Useful next steps include adaptive baselines, multi-switch correlation, rule-expiration telemetry, replayable packet captures, and evaluation under mixed benign workloads. Those additions would test whether the same logic remains stable as traffic diversity increases.

The implementation, attack scripts, evaluator, topology viewer, and demo are available in the [SDN Intrusion Detection System repository](https://github.com/nguyen-nbtk05/SDN-Intrusion-Detection-System).
